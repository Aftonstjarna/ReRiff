# Native recovery with the supplied Ghidra

Use `/var/home/afton/.dev/ghidra_12.2_PUBLIC` inside Distrobox `development`.
This build requires Java 25. The user's supplied
`jdk-25.0.5.0.2` under the Ghidra folder has been verified and is selected by
`ghidra-export.sh`. The container also has `java-25-openjdk-devel` from the
initial setup; subsequent exports use the supplied JDK.
Ghidra rejects project paths containing a dot-prefixed directory such as `.dev`,
so its working project lives at `/tmp/reriff-ghidra/ReRiffNative` inside the
container. Research exports live in the repository's ignored `analysis/ghidra`.

Initial import (original file remains read-only):

```sh
mkdir -p /tmp/reriff-ghidra
/var/home/afton/.dev/ghidra_12.2_PUBLIC/support/analyzeHeadless \
  /tmp/reriff-ghidra ReRiffNative \
  -import "$HOME/.local/share/Steam/steamapps/common/Riff Racer/Game.exe" \
  -processor x86:LE:32:default -cspec windows \
  -analysisTimeoutPerFile 180 -max-cpu 4 \
  -scriptPath /var/home/afton/.dev/ReRiff/Decomp \
  -postScript ExportRecovery.java \
  /var/home/afton/.dev/ReRiff/analysis/ghidra/recovery \
  0048cab0 004a0af0 005282e0 004a22e0
```

For later exports, replace `-import ... -processor ... -cspec ...` with
`-process Game.exe -noanalysis` to reuse the database. Omit `-noanalysis` when
more analysis is required. Check the log for timeouts and decompiler warnings;
successful export does not establish complete or correct program analysis.

The initial whole-program analysis reached its 180-second limit. The database
was saved and targeted exports succeeded; this is partial analysis, not a
completed whole-program pass. Reuse it with the supplied runtime:

```sh
distrobox enter development -- bash -lc \
  'cd /var/home/afton/.dev/ReRiff && bash Decomp/ghidra-export.sh 004a22e0 004a1c30'
```

One observed inference error matters for recovery: initial decompilation of
0x4A22E0 treated the width passed through ECX to 0x4A1C30 as unaffected, showing
zero horizontal padding. The original helper writes through that width pointer
on one branch. The reconstructed assembly preserves both dimensions and both
centering offsets. Do not promote inferred Ghidra prototypes to ground truth.

`ExportRecovery.java` is a small Ghidra API adapter: it hash-checks the original,
exports selected functions and caller/callee references, and labels the output
as research rather than reconstructed source. Ghidra's C output, inferred types
and boundaries must be checked against original instructions and managed IL.
Only source-generated bytes passing the strict comparator enter coverage totals.

ILSpy remains the managed-code tool. The supplied RSI-Anything code-repair
recipe requires a separate benchmark/model environment and custom adaptation
to binary matching; it is not currently used as a decompiler or match oracle.
